# Harness

One run loop, `loop.ts` (main, named workers, messages, versions), over a shell, in one flat `src/`; `tools/` holds every tool and its one registry. The task loop was deleted.

- **Shell:** `loop-shell.ts` (wake-ups, starting a thread, stopping all, the root's end), `threads.ts`, the Pi adapter, `recorder.ts`, `sandbox-session.ts`, `failure-policy.ts` (what a failed main means), and `contracts/thread-records.ts`. `supervise-run.ts` calls `runAgents` (`run-agents.ts`) with the run's parts; the run's bucket is one port, `ports/bucket.ts` (`RunBucket`, one `FileNotFound`), and its adapter is the runner's `store-bucket.ts`.
- **Agent loop state** is `contracts/agents.ts` (`agentLog`): agents, their state (`agentState`, with the caller's `running`), inbox, notices, cursor. Nothing else is held in memory but `handed` (items given to a running thread whose user message is not stored yet; dropped when its invocation settles).
- **Tools** of the agent loop are `tools/` (`registry.ts` is the list). Every id a tool or the loop writes is derived (`effects.ts`), so a repeat or a resume is a no-op.
- `prompts.ts` builds main's and a worker's first messages; the role files are `workflows/core/agents/*.md`. A role file promises only tools in `AGENT_TOOL_NAMES` (`tools/registry.ts`) with the options their schemas have.
- **Review mode** is not a flag: a run is reviewing while a `run.reopened` has no root `completed` end after it (`AgentLog.reviewing`). Then `tools/gate.ts` wraps all of main's tools: a call to a tool with `changesResults` (`start_worker`, `report_output`, `change_outputs`, `keep_output`) is held (`approval.requested` is written with the outputs the tool names and its summary, the call answers "held"), and its batch ends the turn (`ToolContext.batch` is the names in the reply; every other call of a batch holding a flagged name terminates). A yes starts the stored call as a job outside the step's section (`approval-jobs.ts`), which always ends in `approval.settled` (a sandbox that cannot start is retried three times, any other error settles it refused); a no leaves the outputs it named that were undecided at the answer's position in the log to the researcher (a label overlay as its map, once; a decline has no `approval.settled`). `close` is refused while anything is undecided, so a close never withdraws an open request. A user's cancel withdraws only a given call; the outputs stay undecided for the resumed main. An idle main that nothing holds open (`holdsRun`) ends the claim waiting (`idleEnd`; the same step nudges and ends a run stuck when the researcher's message is unanswered); every answer reopens the run. The gate is on the tool, not the role file, and only main is gated: a worker's limit is the `outputs` of its `start_worker` call, enforced in `report_output`.
- **A loop-written id that can recur carries the span** (`AgentLog.span`, the latest `run.reopened`'s id): `recorder.append` ignores an id it holds, so a fixed id from an earlier span would make a step "act" without writing. A step reports acted only if its append wrote (`append` returns whether it did).
- **Skills reach main with a delivery** (`researcher` with the first person notice, `corrections` with the first one or the first out-of-date output in review), given when none of the thread's stored messages holds the block.
