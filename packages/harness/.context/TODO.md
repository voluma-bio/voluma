- **The recorder's failure reaches the supervisor late.** `recorder.failure()` (an event given up on, or an invalid emitted one) is read once per run-loop step, so a running worker's later events are still stored until some thread ends, past the gap. Give the recorder an `onFailure` callback (as `onLeaseLost`) that the run loop wires to its `fail()`, and refuse new events once it is set. Also read `events.failure()` after the final flush in `apps/runner/src/run.ts`, since events emitted after the run loop's last check are only logged.
- **A checker waiting on an unanswered `ask` has no deadline in practice.** Liveness ("no worker or checker running") counts it as not running, so a main that only waits gets `stuckLimit` wakes and the run ends before `checkTimeoutMs`. The wake now names the unanswered asks so main answers them; whether a waiting check should hold the run open until its deadline is open.
- **Some main-tool effects can be left half done by a cut-off.** `message` → `openAttempt` writes the correction revision, the stale marks and `attempt.opened` as separate appends: a cut between them leaves a partial state that only a retry by main repairs, and the retry writes a second correction revision. `stop_worker`: a cut after the stored end and before the task goes `pending` leaves it in-progress while main is told "completed". The loop's own two-step writes (check limit, liveness) recover on the next step. Fix direction: make the loop finish a half-written correction from the log, the way `resumeFeedback` does for feedback.
- **A main↔worker ping-pong is unbounded.** Main keeps messaging an idle worker that never submits, and each idle notice resets the liveness count. There is no default spend cap. A design gap rather than a code bug: bound it (a count of messages per worker without a submit, or a spend cap by default).
