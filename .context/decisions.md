- 2026-10-27: Harness v0 records a thread twice. `pi_messages` holds the model's history, one row per Pi message at `message_end`, written byte for byte and read back unchanged on resume (system message included, never edited); `events` holds the stream record, `seq` allocated inside the insert, a repeated event `id` a no-op, `threads` updated in the same batch. A resumed thread appends another `thread.started` (the projection sets it running again) and answers tool calls a crash left open with error results appended after the history. The `bash` tool's full output is written to `toolOutputKey` from a local temp file in one copy, because the R2 mount cannot append. (harness v0 PR)
- 2026-10-27: Harness event emission is queued and best effort; History is synchronous and an exact prefix. The run's `recorder` delivers `events` in order from a background queue and a failed event never ends a thread; a failed History write aborts the agent and stops persisting, so a resume starts from what the model really saw. `runThread({task, input?})` decides what a resumed thread is sent; a resumed thread whose stored system message differs from the current prompt and tools fails. The runner's routes are under `/run/ingest/` with their own bearer check. ([#9](https://github.com/voluma-bio/voluma/pull/9))
- 2026-10-27: Live output is not an event. `tool.output` left the stored kinds; text deltas, tool-argument deltas and tool output chunks are live frames (`@voluma/contracts/stream`): no `seq`, never stored, replaced by the durable `message` / `tool.result`. Frames are reserved for the review chat's streaming and are not served yet. `message` is split by role: a `user` message has a `sender` (`thread`, `runtime` or `person`), `assistant` and `system` have none; every clearing rule is keyed by an id (`thread.ended` has an optional `messageId`), so event order does not matter; `thread_message` is same-run only, `wait` only toward the sender's own children. ([#11](https://github.com/voluma-bio/voluma/pull/11))

- 2026-10-28: Sign-in is WorkOS AuthKit, handled by the API alone (`apps/api/src/auth.ts`). The root authenticates every `/api/*` request once and sets `principal` (`user` from the session cookie, `service` from the runner's bearer token, which moved out of `domains/run`); domains guard subtrees with `requireService`/`requireUser`. Only members of an allow-listed organization get in (callback and every request): the Yao Lab (scope `lab`) and, if configured, the Judges organization (scope `self`); the scope reaches domains as `readerOf(user)`, never as a branch (`apps/api/AGENTS.md`). Cookie requests that change state need `Origin` equal to `APP_URL` and a JSON content type; bearer requests are exempt. `GET /api/auth/me` returns `{ userId, email, name, labId }`. No `users` table: records store the WorkOS user id. ([#10](https://github.com/voluma-bio/voluma/pull/10))
- 2026-10-28: A task reports typed outputs, not numbers: `report_output` takes a `measurement`, `score`, `structure`, `annotation`, `volume` or `file` (`packages/contracts/src/output.ts`), and the workflow declares each task's outputs in a plan that the run's first `revision.started` carries (`workflowPlanSchema`). A required declared output that is missing keeps the task from `done`; an undeclared one is allowed and marked. `ReviewTask` gains `scores`, `missing` (not structures) and `undeclared`; a declared structure never reported is a `Structure` with status `missing`. The fold has one resolver for references between outputs and drops any that don't resolve; an annotation's `volumeId` is null for the scan, which the API fills. The id schemas and closed vocabularies live in `ids.ts`, a leaf that imports only zod, so contracts files never form an import cycle. ([#16](https://github.com/voluma-bio/voluma/pull/16))
- 2026-10-28: A To check item may carry a `focus` (`focusSchema` in `review.ts`): structure and annotation ids, and optionally a labels `volumeId` with one `label`, a voxel `box` and a `point` ([z, y, x] on the scan's grid), so the review can outline what is under check; absent means the whole task. The fold drops ids that don't resolve. ([#16](https://github.com/voluma-bio/voluma/pull/16))

- 2026-10-28: The runner is a long-running service that claims runs from the API over the bearer ingest routes (`packages/contracts/src/runner.ts`): it polls `claim` every 2 s; every run is created `queued` and only a claim starts it. A claim is a lease of 60 s renewed by a 15 s heartbeat, whose answer says when to stop (cancel, dollar ceiling) and whose body carries the usage since the last one. The lease lives on the run row, judged by the database's `now()`, and each claim issues a token that every ingest write on the run carries (`x-lease-token`); a stale token is a 409 `{code: "lease-lost"}` and the runner stops. A lost lease sends a `voluma` run back to `queued` and a `visitor` run to `awaiting-keys`; three expiries the runner did not explain fail it. Visitor keys travel only in the claim response. The plan's tasks carry `dependsOn`, and `fold` fills it on each folded task (only dependencies that have a row).
- 2026-10-28: The run stream is server-sent events, not a WebSocket: `GET /api/run/runs/:id/stream` sends durable events only (SSE `id` = `seq`, strictly increasing per connection, resumed by `Last-Event-ID` or `?after=`), no snapshot and no frames. Run and task ids may not contain `.`, so thread ids `<runId>.<taskId>.<role>` are unambiguous. A thread that names a task writes only to it. A `judgment` event records each judgment point, its raw decision and the action applied.
- 2026-10-28: The web app is gated on sign-in in the shell (`apps/web/src/shell/signed-in.tsx`): every feature route is a child of the `SignedIn` layout route, which calls `getMe()` and shows the sign-in screen when signed out or after any 401 (`onSignedOut`); `/dev/ui` sits outside it. Features can assume a signed-in user and read it with React Router's `useOutletContext<Me>()` (the gate renders `<Outlet context={me} />`); they never call `getMe` themselves. A sign-in that completes in the page (the demo's visitor) hands its `Me` to the gate through `SignInScreen`'s `onSignedIn`. Until there is a shared top bar, the account menu (name or email, Sign out) is fixed over the top-right corner of every screen, so a feature header should keep that corner clear. (signin-web PR)
- 2026-10-28: Staging is open: every visitor is a guest in one shared workspace in the Demo organization (`GUEST_ORGANIZATION_ID` = `WORKOS_DEMO_ORGANIZATION_ID`, `GUEST_SCOPE=self`: a guest sees only their own runs), never the Yao Lab: lab data is the lab's to share, run by run, so it's visible only to signed-in members; public examples are seeded into the Demo org instead. A guest is a `user` principal with `account: "visitor"` and a server-minted `guest_…` id in its own sealed cookie; `/me` returns `kind: "visitor"`. Only an explicit `POST /api/auth/guest` (same-origin) mints one, which the web gate calls when nobody is signed in; a refused member cookie is a 401 and never becomes a guest. There is no per-visitor mint limit: every run cap is per org. (guest-access PR, on #27)
- 2026-10-28: The host may change later. Cloudflare Workers plus Workflows for the runner is a likely candidate; Jimmy: "no go on workflows experiment right now", so not before the hackathon. So keep the backend portable: plain Postgres through `DATABASE_URL`, SSE or polling rather than WebSockets, no Railway-only features in code (config stays in `deploy.md`), and Web-standard APIs (`fetch`, Web Crypto) where Node-only ones aren't needed. (Jimmy)
- 2026-10-28: The API serves runs (`apps/api/src/domains/run`): the browser routes (start, list, get, cancel, `/keys`, inputs) and the runner's claim, heartbeat and report, with the lease token checked inside every event and history append. Admission and the claim share one Postgres advisory lock and the database's `now()`. Org limits come from `RUN_LIMITS_<LAB|JUDGES|DEMO>_*` env; visitor keys live only in an in-memory vault (capped per org, put there before the start commits), and every claim moves queued visitor runs whose keys its process lacks to `awaiting-keys`. The claim is round-robin by org (the org claimed longest ago first, oldest run within an org); `RUN_LIMITS_<ORG>_VISITOR_ACTIVE` caps an org's unfinished visitor runs. The workflow catalog is code (`catalog.ts`); the reference scan is one `reference-<orgId>` input per allow-listed org, listed to lab-scope readers and readable to a `self` caller through an example run. One API replica only. ([#35](https://github.com/voluma-bio/voluma/pull/35))
