- **The recorder's failure reaches the run loop late.** `recorder.failure()` (an event the store refused, or an invalid emitted one; an unavailable store stops the run as released and sets no failure) is read once per run-loop step, so a running worker's later events are still stored until some thread ends, past the gap. Give the recorder an `onFailure` callback (as `onStop`) that the run loop wires to its `fail()`, and refuse new events once it is set. Also read `events.failure()` after the final flush in `apps/runner/src/run.ts`, since events emitted after the run loop's last check are only logged.
- **A checker waiting on an unanswered `ask` does not hold the run open.** Liveness ("no worker or checker running") counts it as not running, so a main that only waits gets `stuckLimit` nudges and the run ends. The nudge names the unanswered asks so main answers them; whether a waiting check should hold the run open is open.
- **Some main-tool effects can be left half done by a cut-off.** `message` → `openAttempt` writes the correction revision, the stale marks and `attempt.opened` as separate appends: a cut between them leaves a partial state that only a retry by main repairs, and the retry writes a second correction revision. `stop_worker`: a cut after the stored end and before the task goes `pending` leaves it in-progress while main is told "completed". The loop's own two-step writes (liveness) recover on the next step. Fix direction: make the loop finish a half-written correction from the log, the way `resumeFeedback` does for feedback.
- **A main↔worker ping-pong is unbounded.** Main keeps messaging an idle worker that never submits, and each idle notice resets the liveness count. A design gap rather than a code bug: bound it with a count of messages per worker without a submit (there is no spend cap).
- **The run loop's `threadLog` is quadratic in the log's events.** It (and the fold inside it) is derived from the whole log on each change, so a run costs quadratic in its events; fine for hundreds, revisit with the first long run. `threadLog` is a left fold, so it can resume from its cached state and length once the fold does too.
- **`EventLog`, `History` and `HistoryConflict` live in `@voluma/harness`, which drags Pi's dependency tree into `apps/api`.** Move them out so the API stops depending on the harness; the history wire schemas are already in `@voluma/contracts/history`.
- **Live bash output can wait until the command ends.** `tools/bash.ts`'s coalescer checks the 300 ms window only when another chunk arrives. A small first chunk followed by a long silence stays buffered until another chunk or command completion; the live batcher's timer cannot flush text it has not received. Add a timer to the coalescer and clear it on completion or abort.
- **A Claude refusal ends the thread as failed.** On `rawStopReason: "refusal"` (`adapters/pi/start-thread.ts`), retry the turn on Claude Opus 4.8 to stay on Claude, or fall back to Astra.
- **`/inputs` is a writable local copy** where `copiesInputs` is true. Commands run as root, and the sandbox grants no capability to remount or `chattr` it; a non-root user cannot write the FUSE mounts. Revisit if a model edits inputs: mount the staged copy read-only through the image or a mount option.
- **A cold compaction summary of a history larger than the model window is still refused (c699, #315).**
- **`superviseRun` takes `plan` beside `definition` and `selectedOutputs`** (both come from `prepare`). Derive it with `computePlan` inside `superviseRun` once `run-world.ts` can build a plan through `tasks.json`/`outputs.json` (its tests reuse one output id across tasks and mark leaf outputs optional, which `computePlan` cannot express).
- **A new role file still cannot start any other kind of thread.** `threadPlace` (`packages/contracts/src/thread-place.ts`) derives main/worker/check from a start's task and attempt, and `run-loop.ts` starts the entry role as `main`, checks as `check`. Open that to a role named by its file before adding a role with a new shape (a reviewer with no task, a helper under a worker).
- **`redoRefusal` writes one text for two readers.** `fold.ts`'s `redoRefusal(view, taskId)` returns a message naming the task id, which the main agent needs; the API sends the same text as its 409 for a person's go, so the panel can show a raw task id. Return a reason instead, and let each caller word it (the plan title for the person, the id for the agent).
- **History read-time repair leftovers (#385).**
  - A compaction marker cut off in its first ~20 bytes is read as an unreadable message, not a marker, so every later `keptFrom` is off by one. Recognise a prefix of `{"role":"compaction"` as a marker.
  - `unanswered-call` repeats what pi-ai's `transformMessages` already does for unanswered calls (only the wording differs). Keep only `orphan-result`, which Pi lacks, and drop the `close()` half of `repairToolPairs`.
  - Every row is parsed twice per load (`image-refs` and `foldHistory`). Classify once and pass the rows through.
  - Repairs are logged from two places: the row rules in `start-thread.ts` and the pairing rules through `repairLog` in the compactor. Give them one owner.
  - A bad row 0 (system message), or a bad system row that declared tools (`toolsAdded`), still fails the thread as `ThreadStale`. Rebuilding that prompt would change the request bytes.
  - A finished thread whose final reply row is unreadable ends on the placeholder user message, so it counts as unfinished and may run one more turn with no input. `isFinished` can't tell that from a lost mid-run row.
- **Provider-failure follow-ups (PR #378).** The replacement cap (`run-loop.ts`, `startedFor(...).length >= maxFixRounds + 1 + 2`) counts every check of the task over the whole log; fix rounds reset at a correction and on `stale`, the cap does not, so count only checks since the current attempt opened.
- **A crash between `runtime.stop` and `agents.replaceCheck` in `stop_worker` drops the replacement.** Main is told the stop completed and `checks()` writes `CHECK_STOPPED` (to-check); `checks()` could call `replaceCheck` for a check a `stop_worker` effect stopped with no newer check.
- **`interruptedTexts` in `adapters/pi/compaction.ts` is keyed by error text and never cleared.** Harmless while the compactor is made per invocation; one "the last summary call failed after it started" flag, reset on each `summarize`, says the same.
- **`message` resumes of a failed check are not capped** (only `stop_worker` replacements are): a check that keeps failing can be resumed forever by main.
- **A model stream that stalls after its headers is cut by nothing.** No idle timeout covers a reply that has started and goes quiet.
- **Worker `ask` follow-ups (PR #384).** `planChangedText` builds `[...added, ...adHoc]` twice in its callers and its "skipped" part can list nothing for an empty `skip`; a worker's plan-change line is a steer, so a worker that is not running or is cut off before it reads it never hears of the change (deliver from the log like answers if that matters); a worker's `ask` ignores `writeTarget`, so a worker on a skipped or stale task can still ask (its ask is not open, so main is not told, but the event is stored).
- **Stored-id leftovers from the legacy sweep (#386).** The `answer` tool (`tools/main-tools.ts`) still matches an ask by its exact stored id, for asks open in earlier runs; models only see `askRef` names, so drop that half of `named`.

- **One reply can carry more images than a Meta request allows.** `view_image` returns at most 4 images per call, but nothing caps how many calls one reply makes. With 13 or more, the latest turn holds over 50 images; compaction keeps that turn whole (a tool result never starts the kept tail), so even the retry after Meta's 400 sends it again and the thread fails as an overflow. Fix: `view_image` refuses once a batch's images would pass about 40% of the model's per-request count (`maxImages` in `adapters/pi/compaction.ts`). Context: #408, #409.
- `review-assets.ts`: every converter crash is stored as "couldn't write the review files". Use the converter's own last line when it is that sentence, otherwise "the converter crashed: <exception line>" (#436 review).
