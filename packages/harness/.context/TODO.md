- **The recorder's failure reaches the run loop late.** `recorder.failure()` (an event the store refused, or an invalid emitted one; an unavailable store stops the run as released and sets no failure) is read once per run-loop step, so a running worker's later events are still stored until some thread ends, past the gap. Give the recorder an `onFailure` callback (as `onStop`) that the run loop wires to its `fail()`, and refuse new events once it is set. Also read `events.failure()` after the final flush in `apps/runner/src/run.ts`, since events emitted after the run loop's last check are only logged.
- **A checker waiting on an unanswered `ask` does not hold the run open.** Liveness ("no worker or checker running") counts it as not running, so a main that only waits gets `stuckLimit` nudges and the run ends. The nudge names the unanswered asks so main answers them; whether a waiting check should hold the run open is open.
- **Some main-tool effects can be left half done by a cut-off.** `message` → `openAttempt` writes the correction revision, the stale marks and `attempt.opened` as separate appends: a cut between them leaves a partial state that only a retry by main repairs, and the retry writes a second correction revision. `stop_worker`: a cut after the stored end and before the task goes `pending` leaves it in-progress while main is told "completed". The loop's own two-step writes (liveness) recover on the next step. Fix direction: make the loop finish a half-written correction from the log, the way `resumeFeedback` does for feedback.
- **A main↔worker ping-pong is unbounded.** Main keeps messaging an idle worker that never submits, and each idle notice resets the liveness count. A design gap rather than a code bug: bound it with a count of messages per worker without a submit (there is no spend cap).
- **The run loop's `threadLog` is quadratic in the log's events.** It (and the fold inside it) is derived from the whole log on each change, so a run costs quadratic in its events; fine for hundreds, revisit with the first long run. `threadLog` is a left fold, so it can resume from its cached state and length once the fold does too.
- **`EventLog`, `History` and `HistoryConflict` live in `@voluma/harness`, which drags Pi's dependency tree into `apps/api`.** Move them out so the API stops depending on the harness; the history wire schemas are already in `@voluma/contracts/history`.
- **Live bash output can wait until the command ends.** `tools/bash.ts`'s coalescer checks the 300 ms window only when another chunk arrives. A small first chunk followed by a long silence stays buffered until another chunk or command completion; the live batcher's timer cannot flush text it has not received. Add a timer to the coalescer and clear it on completion or abort.
- **A Claude refusal ends the thread as failed.** On `rawStopReason: "refusal"` (`adapters/pi/start-thread.ts`), retry the turn on Claude Opus 4.8 to stay on Claude, or fall back to Astra.
- **`/inputs` is a writable local copy** where `copiesInputs` is true. Commands run as root, and the sandbox grants no capability to remount or `chattr` it; a non-root user cannot write the FUSE mounts. Revisit if a model edits inputs: mount the staged copy read-only through the image or a mount option.
- **Delete the runner's `laidOut` map (`apps/runner/src/run.ts`) in the roles-as-files PR.** It copies each thread's layout from the run loop so the sandbox and log callbacks, which only hold an id, can find a name. Have the sandbox session get its layout from the harness instead.
