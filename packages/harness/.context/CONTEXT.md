# Harness

Two run loops share one shell. `run-loop.ts` is the task loop (tasks, checks, fix rounds); `agents/loop.ts` is the agent model's (main, named workers, messages, versions). A run is pinned to one at its first claim (`root thread.started.harness`).

- **Shared:** `loop-shell.ts` (wake-ups, starting a thread, stopping all, the root's end), `threads.ts`, the Pi adapter, `recorder.ts`, `sandbox-session.ts`, `failure-policy.ts` (what a failed main means), and `contracts/thread-records.ts` (the thread fields both logs read). `supervise-run.ts` picks `tasks-wire.ts` or `agents/wire.ts`.
- **Agent loop state** is `contracts/agents.ts` (`agentLog`): agents, their state (`agentState`, with the caller's `running`), inbox, notices, cursor. Nothing else is held in memory but `handed` (items given to a running thread whose user message is not stored yet; dropped when its invocation settles).
- **Tools** of the agent loop are `agents/tools/` (`registry.ts` is its own list; `report_output` there is not the task loop's). Every id a tool or the loop writes is derived (`agents/effects.ts`), so a repeat or a resume is a no-op.
- `agents/prompts.ts` builds main's and a worker's first messages; the role files are `workflows/core/roles/*.md`. A role file promises only tools in `AGENT_TOOL_NAMES` (`agents/tools/registry.ts`) with the options their schemas have.
- **Review mode** is not a flag: a run is reviewing while a `run.reopened` has no root `completed` end after it (`AgentLog.reviewing`). Then main's calls to tools with `changesResults` (`start_worker`, `report_output`, `change_outputs`, `keep_output`) are held by `tools/gate.ts`: `approval.requested` is written, the call answers "held", and the turn ends (`endsBatch` in `StartThreadOptions` makes the batch's other calls end it too). A yes starts the stored call as a job outside the step's section (`startApproved`), which ends in `approval.settled`; a no triggers `declinedLeaves` (the outputs it named are left to the researcher). An idle main with nothing in flight ends the claim with the waiting end (`waiting`); every answer reopens the run. The gate is on the tool, not the role file, and only main is gated: a worker's limit is the `outputs` of its `start_worker` call, enforced in `report_output`.
- **A loop-written id that can recur carries the span** (`AgentLog.span`, the latest `run.reopened`'s id): `recorder.append` ignores an id it holds, so a fixed id from an earlier span would make a step "act" without writing. A step reports acted only if its append wrote (`append` returns whether it did).
- **Skills reach main with a delivery** (`researcher` with the first person notice, `corrections` with the first one or the first out-of-date output in review), given when none of the thread's stored messages holds the block. Both are `harness: agents` skills: the task loop does not list them.
